# Exhibit contract

Every exhibit on this site is a self-contained ES module in `exhibits/<id>/`. The page shell
lazy-loads it when the visitor scrolls near, mounts it into a dark "stage" panel, and starts and
stops it as it enters and leaves the viewport. This file is the contract between the shell and an
exhibit. `exhibits/_example/` is a minimal working reference.

## Ground rules

1. **Zero dependencies.** No npm packages, no CDNs, no network requests, no image / font / audio
   files. Everything is generated by code in this repository. Plain ES modules, no build step.
2. **Relative URLs only.** The site must work from any base path and from a sandboxed frame:
   `import './x.js'`, `new URL('./style.css', import.meta.url)`,
   `new Worker(new URL('./worker.js', import.meta.url), { type: 'module' })`. Never a leading `/`.
3. **Stay in your folder.** An exhibit owns `exhibits/<id>/` and nothing else. It never styles or
   touches DOM outside the `root` element it is given, and removes any `window`/`document`
   listeners in `destroy()`.

## Module interface

```js
// exhibits/<id>/index.js
export function mount(root, env) {      // may be async
  // root: an empty <div class="stage" data-exhibit="<id>"> already in the document
  // env:  { reducedMotion: boolean, coarse: boolean (touch-first device), small: boolean (viewport ≤ 640px) }
  return { start() {}, stop() {}, destroy() {} };
}
```

- **Complete at rest.** When `mount` resolves, the stage already shows a meaningful still frame,
  even if `start()` is never called. Never leave a blank canvas waiting for input.
- `start()` begins animation / simulation / scheduling. `stop()` halts *all* work (rAF loops,
  timers, worker computation, audio). Both are idempotent and may be called many times.
- Sound may only begin from an explicit tap on a control inside the stage.
- Missing capability (no WebGL2, no float render targets, Worker or WebAssembly blocked): degrade
  to a fallback or show `overlay(view.wrap, { title, text })` with a plain-language message.
  Never an uncaught exception, never a blank stage.

## Building the UI

Use `assets/js/kit.js` (read its JSDoc): `view()` for a responsive DPR-aware canvas, `bar()` plus
`button / toggle / slider / segmented / select / stat / hint / spacer / group` for controls,
`pointer()` for unified mouse + touch + pen (with pinch), `loop()` for rAF, `overlay()` for
messages, `rng(seed)` for determinism, `el()` for DOM. GPU exhibits use `assets/js/glkit.js`
(`createGL`, `program`, `fullscreen`, `target`, `doubleTarget`, `toScreen`, `onContextLoss`).

- Extra styles go in `exhibits/<id>/style.css`, loaded with
  `await loadCSS(new URL('./style.css', import.meta.url))`. Prefix every class with `<id>-`.
- **Colour, type and radius come from tokens** in `assets/css/tokens.css` (`--st-bg`,
  `--st-surface`, `--st-raise`, `--st-line`, `--st-text`, `--st-muted`, `--st-faint`,
  `--st-accent`, `--st-accent-ink`, `--st-accent-soft`, `--st-good/warn/bad`, `--st-c1…c6`,
  `--font-ui`, `--font-mono`, `--font-serif`, `--st-radius-sm`, `--st-control-h`, …). No literal
  colours in CSS. Canvas drawing reads tokens with `cssVar(root, '--st-accent')`. The stage is
  always dark. Content colours inside a rendered scene (a planet, a painting) are of course free.
- **Responsive from 328px to 1120px of stage width.** Controls wrap; nothing overflows
  horizontally; text never clips. On viewports ≤ 640px prefer a taller view
  (`aspectNarrow: 1` or `4 / 5`) and stack side-by-side panels vertically. Check `--mobile`.
- **Touch first.** The owner of this site reads it on an iPhone. Every interaction must work with
  one finger; hover is an enhancement only. Controls are ≥ 40px tall on coarse pointers (the kit
  handles this). Plain wheel/scroll is never captured. Keep a canvas that captures drags no taller
  than ~65% of the viewport so the page can still be scrolled around it.
- **Accessible.** Real `<button>`/`<input>` controls (the kit's are), visible focus, an
  `aria-label` on each canvas (`view({ label })`), text contrast ≥ 4.5:1 against its surface.
- Write UI text plainly, in sentence case. A control says what it does.

## Performance

- Target 60 fps on a laptop and ≥ 30 fps on a recent phone. Cap DPR at 2 (the kit does). Heavy
  shaders adapt their internal resolution to measured frame time (`view.setScale`).
- Never block the main thread for more than ~50 ms. Long computations go in a module Worker, with
  a chunked main-thread fallback if the Worker cannot be created.
- No per-frame allocations in hot loops. No unbounded growth of arrays, DOM nodes or GPU objects.
- When converged or idle, stop drawing (a path tracer that has reached its sample budget should
  not keep the GPU busy).

## Safari / iOS compatibility (cannot be tested in this sandbox, so code defensively)

- JavaScript: nothing newer than ES2021. No regex lookbehind, no `Object.groupBy`, no
  `Array.prototype.with/toSorted`, no `requestIdleCallback`, no `OffscreenCanvas` dependence.
- CSS: no native nesting. `color-mix()`, `:has()`, `aspect-ratio`, `gap`, `dvh/svh` are fine.
- WebGL2: iOS renders to `RGBA16F` but usually cannot linearly filter `RGBA32F`. Prefer
  `rgba16f` (`caps.best`); use `rgba32f` only with `nearest` filtering and only if
  `caps.float32`. GLSL ES 3.00: declare `precision highp float;` (and `highp int` / sampler
  precisions where used), no implicit int↔float conversions, constant loop bounds, initialise
  every variable, avoid `%` on negative ints, guard `pow(x, y)` for x ≤ 0, `sqrt` of negatives,
  division by zero and NaN propagation. Keep loops short enough to compile fast on a phone.
- `gl.readPixels` of float targets is unreliable on iOS: never needed for normal operation; in
  tests, treat an unsupported read-back as "nothing to check" rather than a failure.
- Web Audio: create/resume the `AudioContext` inside the tap handler; set
  `navigator.audioSession.type = 'playback'` when `navigator.audioSession` exists so the iPhone
  silent switch does not mute it.
- WebAssembly: MVP features only. Compilation may be blocked by a sandbox policy: catch and fall
  back.

## Tests

`exhibits/<id>/tests.js` default-exports an array of `{ name, fn, browser? }` built on
`assets/js/check.js` (`assert`, `equal`, `near`, `throws`). The same file runs in Node
(`node tools/test.mjs <id>`) and live in the visitor's browser (the site has a "run the tests"
panel), so:

- keep the logic core in pure modules with no DOM access and test those;
- flag tests that need DOM / WebGL / Web Audio with `browser: true` (Node skips them);
- test real properties (conservation laws, round-trips, differential checks against a reference,
  known closed-form answers), not implementation trivia;
- the whole suite finishes in under ~3 s; no test depends on wall-clock timing or network;
- test names are short plain statements a visitor can read: "a stack of ten boxes comes to rest".

## Development tools

```
node tools/serve.mjs                                   # http://127.0.0.1:4173/dev.html?x=<id>
node tools/test.mjs <id> [-v]                          # Node tests
node tools/shot.mjs '/dev.html?x=<id>' out.png         # desktop screenshot + console-error report
node tools/shot.mjs '/dev.html?x=<id>' out.png --mobile
node tools/shot.mjs '/dev.html?x=<id>&tests' out.png --tests   # also runs browser tests
node tools/shot.mjs '/dev.html?x=<id>&paused' out.png  # the at-rest frame, start() never called
```

`tools/browser.mjs` exports `open(path, opts)` for scripted interaction (Playwright page plus an
`errors` list). The sandbox GPU is a software rasteriser: WebGL2 works but is slow, so judge
correctness and looks there, not frame rate.
